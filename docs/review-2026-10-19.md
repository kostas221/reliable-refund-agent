## Findings

P1 means fix before another evaluation batch. P2 means a concrete correctness or reliability gap to resolve before
claiming the corresponding v1 guarantee. File and function references refer to the reviewed working tree.

### R1 — P1: an interrupted notice is acknowledged without finishing its work

**Where:** `refund_agent/agent/graph.py`, `Agent.notify` (around line 136), and
`refund_agent/agent/notices.py`, `deliver_pending` (around line 76).

The notice ID is checkpointed before the model finishes processing it. If the model then fails, the next delivery
finds that ID and returns immediately. The delivery loop treats that return as success and sets `delivered_at`.
It does not resume the pending graph node.

**Reproduction:** on a fresh PostgreSQL database, propose D01, confirm and approve it, then simulate a model error
on the approval notice. Restore the working scripted model and deliver again. Observed:

```text
FIRST DELIVERY: 0
SECOND DELIVERY AFTER MODEL RECOVERS: 1
NOTICE: [(2, True)]
REFUNDS: [(0,)]
GRAPH PENDING: ('agent',)
```

The customer can remain at approved-but-unpaid although the model recovered. This does not create a duplicate
payment; it breaks automatic continuation. The existing duplicate-delivery test covers a completed graph run,
while the failure test substitutes a notifier that fails before checkpointing anything.

**Change:** distinguish recording an event from completing its handling. Under the conversation lock, resume
pending work for an already recorded notice before acknowledging it; only skip a completed notice. Keep retries
bounded and make exhausted deliveries visible to staff. Test interruption before execution and after commit but
before the checkpoint, followed by automatic delivery/restart, without a manual `Agent.resume()` call.

### R2 — P1: simulator faults remove safety failures from the headline failure count

**Where:** `refund_agent/evaluation/audit.py`, `Audited.outcome` (lines 74–85).

The `invalid`/`simulator_fault` branch runs before the failed-verdict branch. A conversation with a committed
unauthorized refund and a simulator fault therefore becomes `not_a_test`.

**Reproduction:** construct a failed `forbidden:unauthorized_refund` item and set `simulator_fault=True`.
The report says `0 failed`, `1 not a test`, and no scenario failed. The detailed machine-failure list still shows
the violation, so the evidence is not erased, but the summary and scenario classification contradict it.

**Change:** represent simulation validity separately from safety outcome. An unauthorized or duplicate committed
effect remains a safety failure in every denominator where safety is reported, even with simulator/provider/budget
problems. Conditional task-success statistics may exclude invalid simulations while retaining those safety counts.
Add combined-fault tests, not only one-fault-at-a-time cases. This is explicitly required by plan section 11.

### R3 — P1: an unexpected run failure can destroy its database before a result is saved

**Where:** `refund_agent/evaluation/pilot.py`, `paid_run` (around lines 188–197), and
`refund_agent/evaluation/runner.py`, `run_scenario` exception handling.

The pilot drops the attempt database in `finally`, then calls `_save`. A database exception or another unexpected
failure in the graph/evaluator escapes the runner's narrow exception handlers. The cleanup runs, but `_save` is
never reached. A failure while writing the result also occurs after the database has been removed.

**Reproduction:** execute the actual pilot control flow with all providers and database operations replaced by
fakes, and raise an unexpected exception from `run_scenario`. Observed:

```text
RETENTION: ['DROP refund_pilot_run', 'DROP refund_pilot_template']
SAVED RESULTS: 0
```

This probe spent nothing. In a real run, earlier requests or committed operations could already exist. Request
logs may survive, but they are not a saved trial outcome or a substitute for the lost business-state evidence.

**Change:** create a durable trial record before starting, preserve infrastructure failures and counted/uncertain
cost, and write the result/state evidence atomically before destructive cleanup. If evidence export fails, retain
that attempt database for diagnosis. Preserve the original failure if cleanup also fails. Test unexpected runner
errors, result-file write failure, and interruption after a committed operation.

### R4 — P2: incomplete repeat sets can be presented as success in every try

**Where:** `refund_agent/evaluation/audit.py`, `conversations` and `report` (around lines 104 and 189).

The report discovers only existing `result.json` files. It never checks the manifest's planned scenarios/repeats.
If only a successful `try1` remains from a planned three-try scenario, it reports that scenario as passed in every
try (`pass^k`). The missing attempts disappear from the denominator.

**Reproduction:** pass one successful audited attempt to the report: `pass^k: 1 of 1`, with no unsettled scenario.
The report has no argument or manifest read through which to distinguish a complete one-repeat run from a partial
three-repeat run.

**Change:** enumerate expected trial IDs from the manifest; report missing, interrupted and duplicate attempts
explicitly. Compute pass^3 only for complete triples and retain the planned scenario denominator. Test a missing
try, an entirely missing scenario and duplicate trial IDs.

### R5 — P2: reaching a conversation limit looks like a normal ending

**Where:** `refund_agent/evaluation/runner.py`, the `max_rounds` loop (around line 88), and
`refund_agent/evaluation/customers.py`, `SimulatedCustomer.next_line` (around line 75).

Exhausting the round loop records no termination error. Exhausting the simulator's message allowance returns the
same `None` used for a voluntary end. Some scenarios can therefore have no machine failure although the customer
was cut off by the harness.

**Reproduction:** run D07 on PostgreSQL with a scripted customer that has another message queued, a model that
keeps refusing foreign access, and `max_rounds=1`. Observed `system_error=None`, `simulator_error=None`, no failed
machine items, and one customer message still queued. This establishes the classification gap, not an observed
failure in the paid pilots.

**Change:** save a structured termination reason, distinguish normal completion from agent/round/simulator limits,
and handle each explicitly in the report. Keep the outcome and safety evidence even when a limit is hit. Add
per-conversation call/time counters with the final runner, rather than relying only on per-turn graph limits.

### R6 — P2: the claimed worst-case budget is a heuristic

**Where:** `refund_agent/agent/costs.py`, `estimated_tokens` (line 35), and
`refund_agent/agent/openai_adapter.py`, `worst_case_usd` (line 133).

`len(text) // 3 + 1` is not an upper bound on token usage. IDs, punctuation, Unicode and provider continuation
content need not follow the assumed average. `settle` accepts reported usage even when it exceeds the estimate.

**Reproduction:** with a fake provider only, an estimated $0.0001074 request was admitted under a $0.0002 limit;
reported input usage then settled at $0.0003. This proves that the implementation does not enforce the advertised
hard bound; it does not claim that any saved live pilot exceeded its cap.

**Change:** use defensible input accounting with explicit overhead and a conservative allowance, plus an input
size limit. Treat an estimate overrun as a recorded exceptional condition that prevents further calls. Until the
bound is justified, describe it as an estimated budget guard. The dry-run estimate also assumes 12 agent requests
per scenario, while the graph permits that many per turn, and does not include all retries; label that estimate
accurately or derive it from the enforced whole-conversation limits.

### R7 — P2: simultaneous CLI runs share destructively recreated databases

**Where:** `refund_agent/evaluation/pilot.py:44`, `refund_agent/evaluation/mock.py:23`, and
`refund_agent/db.py`, `create_database`/`drop_database`.

Every pilot uses `refund_pilot_template` and `refund_pilot_run`; every mock invocation likewise shares fixed names.
`create_database` first force-drops the named database. A second invocation can terminate the first one's work.
Unique output directories do not isolate their databases. This follows directly from control flow; no concurrent
paid run was started to demonstrate it.

**Change:** give every batch and trial a unique database name, record ownership, and clean up only that batch's
databases. Alternatively refuse a second invocation using an explicit run lock. The test fixtures already use
unique names and provide a suitable pattern. Test two concurrent fake-provider runs.

### R8 — P2: a late polling response can overwrite newer state on screen

**Where:** `frontend/src/polling.ts`, `refresh` (around lines 23–37).

The generation counter protects changes of resource key, but not overlapping reads of the same key. The timer
avoids starting a poll while another read is active; explicit refresh after an action does not. Both responses
can update state, in arrival order.

**Reproduction:** execute the actual hook body with controlled promises and hook substitutes. Start an old read,
then refresh; complete the new response with `refunded`, then the older response with
`awaiting_staff_approval`. The displayed data changes back to `awaiting_staff_approval`.

**Change:** give requests a monotonically increasing generation and accept only the current response, or serialize
reads with a queued refresh after mutations. Make the loading flag belong to the correct request. Add a test with
responses arriving in reverse order. Backend checks prevent stale buttons from authorizing a second refund, but
the screen currently gives the customer/staff misleading status until another refresh.

### R9 — P2: the privacy pre-check still uses timestamps instead of message sequence

**Where:** `refund_agent/evaluation/evaluator.py`, `_foreign_data` (around line 472).

The check excuses information if a customer message has `m.at <= message.at`. When two messages share a timestamp,
a customer who repeats data after the agent disclosed it is incorrectly treated as having supplied it first.
The messages already carry `seq` specifically to resolve such ordering.

**Reproduction:** agent reveals the other customer's D07 email at sequence 1; customer repeats it at sequence 2,
with the same timestamp. No exact disclosure is found. Change only the customer's timestamp to a later time and
the disclosure is found. The dialogue-audit item remains pending in the first case, so this is a weakened machine
check rather than an automatic final pass.

**Change:** use `m.seq < message.seq`. Add same-time cases in both orders.

### R10 — P2: the run fingerprint omits code that determines the database

**Where:** `refund_agent/evaluation/manifest.py`, `RUN_FILES` (around line 20).

The fingerprint includes SQL files but omits `refund_agent/db.py`, `migrations/env.py` and migration version
wrappers, all of which decide how that SQL/checkpoint setup is applied. `pyproject.toml` is also omitted. Recording
`git_dirty=True` says something changed but does not identify the changed content.

**Reproduction:** in a temporary root, change only `refund_agent/db.py`. `fingerprint(file_hashes(root))` remains
identical. No real project file was changed for this probe.

**Change:** include all executable setup code and effective dependency/runtime configuration, with tests that
change one important file at a time. The final runner also needs the actual held-out fixtures, freeze manifest and
data provenance hashed; their absence from this development-pilot manifest must not be carried into final runs.
Audit saved runs against their recorded scenario snapshots, rather than silently depending on current files.

### R11 — P2: the local database port is published on all host interfaces

**Where:** `docker-compose.yml:13`, `"5433:5432"`.

The project describes a local demo with known test database passwords. Its port mapping does not restrict binding
to loopback. Actual access from another machine depends on the host firewall/network, but the Compose definition
itself does not enforce the stated local boundary.

**Change:** use `"127.0.0.1:5433:5432"` for the current local workflow. Keep service-to-service access inside the
Docker network when the full stack is packaged. Check the effective binding; do not claim public deployment
security from these local settings.

## Recommended order

Fix R1 first, then R2–R5 so recovery and the report cannot silently lose or misclassify work. Resolve R6–R7 and R10
before another paid batch. Fix R8–R9 and the small loopback change R11 with focused regressions. Complete the
remaining phase 6 gates, validate the stable revision, and only then proceed to the frozen evaluation.

Keep the existing architectural choices: backend authority, immutable proposals, integer amounts, transactional
receipts/ledger, unique unit and approval constraints, independent evaluator expectations, real-database race
tests and mock operation. The findings call for specific corrections and completion of existing commitments,
not a replacement architecture.
